When we shipped the first version of our conversational assistant for the
University of Mississippi, we implemented a textbook RAG pipeline: embed the
knowledge base, retrieve the top-k passages, and answer from them. It worked,
until the conditions were different.

We discovered two failure modes in our initial approach:

- **Stale answers:** anything that had changed after the last index (deadlines,
  office hours, etc.) was answered incorrectly, as the retrieval step could only
  return information known at indexing time.
- **Confident hallucinations:** when the retrieval returned weak matches, the
  model often answered confidently, inventing information to fill in the gaps.

Pure web search has the inverse problem: it can return fresh information but has
no grounding in the university's documents and policies.

## The idea: route instead of choose

The solution was a routing layer rather than a choice between sources. We gave
the agent a tool for each and let it decide based on the query. The retrieval
layer became a small routing step:

- The knowledge base is used to answer questions about stable, authoritative
  information (policies, program requirements, and internal documents).
- Live web search is used for any time-sensitive information.
- Both are used when the question spans the two: retrieve the policy, then check
  the current date or status.

The router itself could be a cheap classification call, which saves the
expensive model for answering rather than deciding:

```python
def route(question: str) -> list[str]:
    """Pick retrieval tools. Cheap model, strict output."""
    decision = classify(question, labels=["kb", "web", "both"])
    if decision == "both":
        return ["knowledge_base", "web_search"]
    return ["knowledge_base" if decision == "kb" else "web_search"]
```

## Grounding is the part that matters

Routing only helps if we force the final answer to be grounded in the retrieved
evidence. Two rules of thumb made most of the difference:

- Every claim in the answer must trace back to a retrieved passage or search
  result.
- If the evidence is missing or contradictory, the agent should say so and offer
  a human contact instead of guessing.

That second rule is what moved the hallucination rate. Measuring it was
unglamorous, but we eventually logged answers and labelled whether each was
supported by the retrieved context. The supported-answer rate increased by more
than 90% compared to the original pipeline.

## What I'd keep

- **A separate routing step.** Giving the answering model the option to pick
  tools made it worse at both jobs.
- **A hard grounding contract.** "Answer only from context, otherwise escalate"
  beats any amount of prompt polishing.
- **Multi-channel delivery.** The agent runs on Web, WhatsApp and Telegram. The
  routing and grounding logic is the same in all, implemented as a single
  service and thin adapters on each channel.

The interesting lesson is that the hard part of a RAG agent isn't the retrieval
algorithm. It's the question of what to retrieve, and the discipline not to
answer when you have nothing solid to stand on.
