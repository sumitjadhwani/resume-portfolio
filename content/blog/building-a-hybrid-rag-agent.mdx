When we shipped a conversational assistant for the University of Mississippi, the
first version was a textbook RAG pipeline: embed the knowledge base, retrieve the
top-k passages, and let the model answer from them. It worked. Until it didn't.

Two failure modes showed up almost immediately:

1. **Stale answers.** Anything that changed after the last index (deadlines,
   office hours, policy updates) came back wrong, because retrieval can only
   return what was indexed.
2. **Confident gaps.** When retrieval returned weak matches, the model still
   answered, inventing details to fill the space.

Pure web search had the opposite problem: fresh information, but no grounding in
the university's own documents and policies.

## The idea: route instead of choose

Rather than picking one retrieval source, we gave the agent a tool for each and
let it decide per query. The retrieval layer became a small routing step:

- **Knowledge base** for stable, authoritative content (policies, program
  requirements, internal docs).
- **Live web search** for anything time-sensitive.
- **Both** when a question spans the two: retrieve the policy, then check the
  current date or status.

The router itself can be a cheap classification call, which keeps the expensive
model for answering rather than deciding:

```python
def route(question: str) -> list[str]:
    """Pick retrieval tools. Cheap model, strict output."""
    decision = classify(question, labels=["kb", "web", "both"])
    if decision == "both":
        return ["knowledge_base", "web_search"]
    return ["knowledge_base" if decision == "kb" else "web_search"]
```

## Grounding is the part that matters

Routing only helps if the final answer is forced to stand on the retrieved
evidence. Two rules did most of the work:

- Every claim in the answer must trace back to a retrieved passage or search
  result.
- If the evidence is missing or contradictory, the agent says so and offers a
  human contact instead of guessing.

That second rule is what moved the hallucination rate. Measuring it was
unglamorous. We logged answers, labelled whether each was supported by the
retrieved context, and iterated. The supported-answer rate went up by more than
90% relative to the original pipeline.

## What I'd keep

- **A separate routing step.** Letting the answering model also choose tools
  made both jobs worse.
- **A hard grounding contract.** "Answer only from context, otherwise escalate"
  beats any amount of prompt polishing.
- **Multi-channel delivery.** The same agent ran on Web, WhatsApp and Telegram.
  The routing and grounding logic lived in one service, so each channel was just
  a thin adapter.

The interesting lesson is that the hard part of a RAG agent isn't the retrieval
algorithm. It's deciding _what to retrieve_, and being disciplined about not
answering when you have nothing solid to stand on.
